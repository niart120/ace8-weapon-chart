# 武器別確定数一覧 初期設計仕様書

更新日: 2026-11-03。初期実装に着手。合意済みの要件と、今後決める内容を分けて記録する。

## 1. 概要

### 1.1 目的

エースコンバット8のキャンペーンで、HP満タンの目標を撃破するために必要な同一兵装の命中数を一覧表示する。目標を行、兵装を列に配置する。

### 1.2 用語定義

| 用語 | 定義 |
| --- | --- |
| 確定数 | 同一条件で同じ兵装を命中させ、HP満タンの目標1体を撃破するために必要な命中弾数。発射操作の回数ではない |
| 子弾の確定数 | SFFS・SODの子弾1発を単位として数える、撃破に必要な命中数 |
| TLSの命中時間 | TLSで撃破するまでに必要な命中時間。秒で表示する。初回命中と継続命中の時刻の扱いは計算設計で確定する |
| 命中条件 | 直撃、爆風、直撃＋爆風のいずれか。直撃＋爆風は同じ目標に両成分が入る計算条件 |
| 爆風成分 | 直撃とは別に適用される追加の範囲ダメージ。爆弾本来の範囲攻撃とは区別する |

### 1.3 背景・問題

`docs/initial/mock.xlsx` に、自機種別・強化パーツ・兵装分類の選択欄と、目標別の確定数表がある。`src/App.tsx` はひな形の状態で、武器データや確定数計算は未実装。

参照資料では、目標のHP・耐性に任務差分があり、兵装によって直撃・爆風・継続・子弾の扱いが異なる。資料の検証範囲は静的解析であり、実ゲームでのダメージ測定は未実施。

### 1.4 期待効果

| 項目 | 期待効果 |
| --- | --- |
| 兵装の比較 | 同じ目標に対する必要命中数を一覧で比較できる |
| 条件の比較 | 自機種別や強化パーツ、命中条件に応じた値を確認できる |

## 3. 設計方針

### 3.1 対象目標

キャンペーンの通常目標、任務固有の目標、大型兵器の各部位を対象とする。同名でもHPや耐性が異なる目標は、条件が分かる別の行として扱う。

任務による差分・部位は表示と非表示を切り替えられるようにする。

「任務差分」は、同じ目標でも任務によってHPや耐性が異なる設定を指す。チェックボックスをオンにすると、共通設定の行を残したまま、ミッションを示すラベル付きの任務固有行を追加表示する。各行には、その行のHP・耐性で計算した確定数を表示する。HPが同じで耐性だけ異なる場合も別行とする。この表示方式は合意済み。ミッション・部位のラベル記法は3.4に従う。

「部位」は、大型航空機・艦船・陸上大型兵器・施設などの破壊可能な構成部分を指す。部位の行は、全体共通の1つのチェックボックスで一括表示・非表示にする。本体と部位の両方に行がある目標では、このチェックボックスで切り替えるのは部位の行とする。この方式は合意済み。

同じ本体・任務条件の中で、表示名と計算条件が等しい複数の部位定義は、左右などの配置差だけでは表示行を分けず、1つの項目にまとめる。これはエンジンに限定しない部位全般の方針とする。元の各定義への参照は保持する。表示する値は部位1つを撃破するための確定数とし、まとめた部位のHPや必要命中数を合算しない。HP・耐性など計算条件に差がある部位は、表示名が同じでも別行とする。

初回表示では、任務差分・部位のチェックボックスを両方オフにする。画面ラベルは、任務差分を `MISSION VARIANTS`、部位を `TARGET PARTS` として当面採用する。和訳案の比較検討は[ISSUE-003](ISSUES.md#issue-003-表示切り替えラベルの和訳案)に残す。両チェックボックスは、目標選択を行う `TARGETS` 内に配置する。

任務差分と部位の両方に該当する行は、`MISSION VARIANTS` と `TARGET PARTS` が両方オンのときだけ表示する。同じ部位に共通設定と任務固有設定がある場合、共通設定の部位行は `TARGET PARTS` がオンなら表示し、任務固有設定の部位行には両方のオンを要求する。いずれも3.9で個別に選択されていることを表示条件とする。兵装側の選択と目標分類による一括選択も、それぞれの条件に従って適用する。

### 3.2 命中条件

「直撃／爆風／直撃＋爆風」の3段切り替えを表全体で共通の1つとして設ける。初期値は「直撃」。兵装ごとの個別切り替えは設けない。

画面の見出しは `DAMAGE TYPE`。選択肢は `DIRECT`・`BLAST`・`DIRECT+BLAST` とし、それぞれ直撃・爆風・直撃＋爆風に対応させる。初回は `DIRECT` を選択する。

直撃と爆風は成分ごとに補正とHP更新を扱う。両成分を合算してから一律の補正を掛ける計算にはしない。直撃＋爆風は、両方が同じ目標に入ると仮定した計算条件であり、全命中で成立する保証ではない。この説明はドキュメントに置く。

切り替えはSASM・LAGM・LASM・LACM・MPBMに適用する。MPBMでは爆風側に範囲初撃を対応させ、継続ダメージは含めない。

追加爆風を持たない兵装は、選択した命中条件にかかわらず、その兵装本来の計算結果を表示する。MSL・TLS・UGBなどは「爆風」を選んでも比較対象として残る。UGBなどの基礎威力に含まれる範囲攻撃は、追加爆風と区別して計算に含める。

### 3.3 特殊なダメージ形式

| 兵装 | 合意した計算・表示 |
| --- | --- |
| MPBM | 直撃・範囲初撃を計算対象とし、継続ダメージは評価対象外とする。未対応課題として残す |
| TLS | 確定数ではなく、撃破に必要な命中時間を秒で表示する。列名称は `TLS [s]` とする |
| SFFS・SOD | 子弾1発の威力を使い、撃破に必要な子弾の命中数を表示する。ダメージ値自体や親兵装の投下数は表示値にしない |

MPBMの継続分を除外する条件、TLSの計算条件、SFFS・SODが子弾単位であることはドキュメントに記載し、画面上の説明文にはしない。

UAVTの評価方法と計算単位は未決定。「理論上の最大ダメージを基準に評価する」案は、未採用の候補として[ISSUE-005](ISSUES.md#issue-005-uavtの評価方法と計算単位)に保持する。最大ダメージの評価範囲と、セルに表示する値の意味は調査後に協議する。

### 3.4 画面上の文章

画面は、操作ラベル・目標名・兵装名・数値・単位を基本とする。説明文や注意文を常設しない。計算前提、対応範囲、未対応事項の説明はドキュメントに置く。

`TLS [s]` のように、列名称と単位で値の意味を区別する。説明文を別の画面部品へ移して表示する方針は採用していない。

画面ラベルには英語・略号を用いる。ゲーム由来の名称は、確認できた表示名・略号に合わせる。内部の識別子を大文字にしただけで表示名として採用しない。必要な名称の確定に向けた実アプリ解析はユーザーから許可されている。

2026-11-03に、同梱の日本語モード用文字列データと兵装・パーツ定義を照合した。自機種別の収録表記は `FIGHTER`・`ATTACKER`・`MULTIROLE`・`ELECTRONIC WARFARE`。威力強化パーツ10種の略号は[表示名の調査記録](../../../../docs/analysis/ui-labels/UI_LABELS.md)に記載した。今回の確認は同梱資料の静的解析であり、ゲーム画面の実行確認ではない。

`TLS [s]` と機銃の `TypeA`・`TypeB`・`TypeC` は個別に合意した表記を維持する。アプリ独自の分類名や操作の呼び方は別途協議し、仕様書に記載しただけでは画面上の表記として採用したとは扱わない。

目標行のミッションラベルと部位ラベルは、囲い文字を変えて区別する方針とする。ミッションの表示ラベルに `Day 1` は付けない。元資料の任務識別子は表示用ラベルとは区別し、表示の省略によって異なる定義を統合しない。

部位の記法は `部位名《本体名》` とする。例は `MAIN ENGINE《LADON》`。部位名を先頭に置き、その部位が属する機体・艦船・施設などの本体名を二重山括弧 `《》` で囲む。部位名と開き括弧の間に空白は入れない。部位ではない本体の行には、この括弧を付けない。

ミッションラベルは `[M番号]` とし、目標名または部位表記の末尾に半角空白を挟んで付ける。併記例は `MAIN ENGINE《LADON》 [M16]`、部位ではない目標の例は `X-40 [M29]`。この記法と順序は合意済み。

### 3.5 自機種別と強化パーツ

自機は、戦闘機・攻撃機・マルチロール機・電子戦機の種別から1つを選択する。威力強化パーツはそれぞれ個別にオン・オフを選択し、補正を自由に組み合わせて比較できるようにする。

自機種別の見出しは `ROLE`。PC版では `FIGHTER`・`ATTACKER`・`MULTIROLE`・`ELECTRONIC WARFARE` を横に並べ、1つだけ選択する切り替えとする。選択中の項目を視覚的に区別できるようにする。初回の選択は `FIGHTER`。

強化パーツの見出しは `PARTS`。各パーツをチェックボックスで個別にオン・オフし、ラベルには `MSL.POW+` など確認済みのゲーム内略号を使用する。初回はすべてオフとし、選択したパーツの補正をその場で一覧に反映する。

実際の機体への搭載可否やパーツスロット制限による選択制限は設けない。選択した条件を各兵装の計算に適用し、実際に装備可能な構成の再現は対象としない。自機種別とパーツ名の表記は3.4に従う。

### 3.6 難易度差のある兵装

通常版のMSLとRookie版のMSLを別の兵装定義として持ち、`WEAPONS` の個別選択へ統合する。基礎威力は通常版が40、Rookie版が56。同時に選択して別列で比較できる。この方針は合意済み。`DIFFICULTY BONUS` と `Rookie (Story)` チェックボックスによる専用操作は廃止し、独立したRookieフラグは保持しない。`MSL(Rookie)` は説明用の呼称とし、結果列・選択肢の具体的なラベル表記は別途決める。

ゲーム内の難易度名は、ユーザー提示の `Rookie(Story)`・`Pilot`・`Veteran`・`Elite`・`Ace` として把握する。これまでの議論と参照資料で `CASUAL` と呼んでいた基礎威力の差は、上記の別兵装定義で扱う。元資料の呼称やテーブル行名は証跡として保持し、ゲーム内表示名とは区別する。

当面は難易度による敵HPの変化を計算に設けない。参照資料の `DT_NPC_Difficulty.json` では、キャンペーンの難易度5行すべてで `MaxHealth` が1.0であることを確認した。ただし、別の初期化処理や任務イベントを含む全経路でHPが変わらないことまでは確認していない。[ISSUE-002](ISSUES.md#issue-002-難易度による敵hp変化の有無)を要調査として残し、差が確認された場合は計算条件を見直す。この調査状況は画面上の説明文にはしない。

### 3.7 機銃の種類

機銃の `TypeA`・`TypeB`・`TypeC` は、それぞれ別のIDを持つ兵装定義として `WEAPONS` で選択する。複数Typeを同時に選択して別列で比較できる。この方針は合意済み。基礎名は共通の `GUN` とし、種類の表記を含む選択肢・列ラベルの記法は別途決める。

元データの順序に合わせて、当面は `TypeA` を `BP_plwp_gun_x0_C`（基礎威力5）、`TypeB` を `BP_plwp_gun_x1_C`（基礎威力15）、`TypeC` を `BP_plwp_gun_x2_C`（基礎威力10）に対応させる。この対応はアプリ上の区分として合意したものであり、ゲーム内の正式なType名称との一致を確認したものではない。

`GUN TYPE` の専用スイッチと、独立した機銃Typeの状態は廃止する。各Typeの選択は他の兵装と同じ選択状態として保存・復元する。初期選択は3.8に従う。機銃の種類の説明はドキュメントに置き、画面には選択ラベルと計算結果を表示する。

`[威力]<発射レート>` 形式の代替ラベル案は、未採用の候補として[設計メモ](../../notes/dev-journal.md)に残す。当面は上記の表記で進め、全体完成後の見直し候補とする。

### 3.8 表示する兵装の絞り込み

PC・スマートフォンともに `WEAPONS` ボタンから、同じ見出しの兵装選択パネルを画面右側に重ねて開く。PCでは画面右側の一部、スマートフォンでは画面幅いっぱいを使う。選択欄では分類ごとの見出しの下に兵装ごとのチェックボックスを並べ、表示する兵装を個別に複数選択する。選択変更は即時反映し、選択欄を閉じると結果一覧に戻る。兵装候補の一覧は主画面に常設しない。

PC版もこの操作に統一する。分類は兵装を探すためのまとまりとして使用し、表示列は個々の兵装の選択状態で決める。

MSLの通常版・Rookie版、機銃の各Typeも、それぞれ個別の兵装選択項目として扱う。同系統の設定違いを複数選択して別列で表示でき、一方を選んでも他方を自動解除しない。MSLの両定義は `MSL` 分類、機銃の3定義は `GUN` 分類に含め、一括選択・解除と名前検索も通常の兵装と同じ規則を使う。

両端末とも、分類見出しにチェックボックスを設け、その分類の表示対象兵装を一括選択・解除できるようにする。個々の兵装の選択状態から、分類のチェックボックスを全選択・未選択・一部選択の中間状態で表示する。未選択または中間状態からの操作は全選択、全選択からの操作は全解除とし、他分類の選択状態は保持する。個別兵装のチェックボックスも引き続き操作できるようにする。

PC・スマートフォンともに、分類ごとに配下の項目を展開・折りたたみできるようにする。分類名または開閉アイコンで開閉し、分類のチェックボックスによる一括選択・解除とは別の操作にする。開閉だけでは兵装の選択状態と結果表の表示列を変更しない。この操作は `TARGETS` にも共通して適用する。

表示対象の兵装・分類対応・分類内の並び順は次のとおりで合意した。`OTHER` の括りは当面の分類として採用する。設定違いのラベルは説明用の表記とする。

| ラベル | 含める兵装 |
| --- | --- |
| `MSL` | MSL、MSL(Rookie) |
| `MSL.AIR` | 2AAM、4AAM、6AAM、8AAM、HCAA、HPAA、HVAA、LAAM、QAAM、SAAM、SASM |
| `MSL.GND` | 4AGM、6AGM、8AGM、LACM、LAGM、LASM |
| `BOMB` | GPB、SFFS、SOD、UGB、UGBL、XSDB |
| `GUN` | GUN TypeA、GUN TypeB、GUN TypeC、MGP |
| `RKT` | RKT |
| `OTHER` | EMLB、MPBM、TLS、UAVT |

結果表の兵装列と `WEAPONS` の選択欄は、`MSL → MSL.AIR → MSL.GND → BOMB → GUN → RKT → OTHER` の分類順を共通にする。選択解除・再選択しても同じ位置に戻る固定順とする。この方針は合意済み。分類内は略号順を基本とし、数字で始まる同系統の兵装は数値順とする。MSLは通常版→Rookie版、GUNはTypeA→TypeB→TypeC→MGPの順とし、設定違いを隣接させる。上表の順序をマスタの表示順として保持し、ID順や選択した順から並びを決めない。

ESM・ECM・IEWSなどの支援兵装は、確定数の比較列と `WEAPONS` の選択候補から除外する。この方針は合意済み。支援兵装を一覧の対象に含めない判断として扱い、未解禁兵装を表す `UNUSED` の分類とは区別する。表示する各目標に対して `-` や独立した「対象外」セルを並べる構成にはしない。

単発EML・PLSL・ADMMは、ユーザーからの「現時点ではゲーム内で未解禁」という情報に基づき、`UNUSED` に分類して保持する。PGUN・EMLT・UAVG・UAVP・FAEBも、ユーザー指定により `UNUSED` とする。現時点の一覧表と兵装選択欄には含めず、表示分類の兵装候補にも表示しない。元の定義・参照資料を削除するものではない。ゲーム内の解禁状況を今回の静的調査で独立に検証したわけではない。

対象の定義は次のとおり。表示略号だけで判定しない。

初期選択には従来の端末別ルールを適用する。PC版は設定違いを含む表示対象の全兵装を選択し、スマートフォン版は通常版の `MSL` のみを選択する。PC版ではRookie版MSLと機銃3種類も初期選択に含む。`UNUSED` は初期選択にも含めない。兵装をすべて未選択にする操作を許可し、その場合は兵装列をすべて隠して目標名・HP列を残す。選択を自動的に戻さず、操作欄は引き続き使用できるようにする。表示対象は上記の合意済み一覧に従う。目標側の絞り込みとは独立して操作する。

### 3.9 表示する目標の絞り込み

目標も分類ごとの一括選択と、個々の目標の複数選択に対応する。PC・スマートフォンともに、表の上で `WEAPONS` と並ぶ `TARGETS` ボタンから、同じ見出しの目標選択パネルを画面右側に重ねて開く。兵装側と同じく、PCでは画面右側の一部、スマートフォンでは画面幅いっぱいを使う。分類の下に個別目標のチェックボックスを並べる。兵装側の選択とは独立して操作し、一方の選択を変更しても、もう一方の選択状態は保持する。

分類のチェックボックスは兵装側と同じく、全選択・未選択・一部選択の中間状態を表す。未選択または中間状態からの操作は全選択、全選択からの操作は全解除とし、他分類の選択は保持する。選択変更は即時反映する。

分類の展開・折りたたみは3.8と同じ操作とし、分類名または開閉アイコンで切り替える。開閉だけでは個別目標の選択状態と結果表の表示行を変更しない。折りたたみ中も、分類のチェックボックスから一括選択・解除できるようにする。

`MISSION VARIANTS`・`TARGET PARTS` は目標選択パネル内にまとめ、一覧表の直前には常設しない。パネル内の具体的な配置は確認中。

初回は表示対象の5分類に含まれる目標をすべて選択する。`EXCLUDED` は初期選択にも含めない。`MISSION VARIANTS`・`TARGET PARTS` は3.1のとおり初回はオフとする。全目標を未選択にする操作を許可し、その場合は表の見出しだけ残してデータ行を表示しない。選択を自動的に戻さず、操作欄は引き続き使用できるようにする。兵装・目標の全解除時も「対象がありません」などの説明文は表示しない。分類と各目標の対応は今後決める。

共通行・任務差分行・部位行は、それぞれ独立した選択項目とする。任務差分・部位は3.4のラベル記法で区別し、本体や共通行とは別に個別選択できる。この選択単位は合意済み。例えば `LADON`、`MAIN ENGINE《LADON》`、`MAIN ENGINE《LADON》 [M16]` は、それぞれ独立したチェックボックスを持つ。

`MISSION VARIANTS`・`TARGET PARTS` をオフにすると、該当行を選択候補と一覧の両方から隠す。表示切り替えだけでは個々の項目のチェック状態を変更せず、選択・未選択を保持する。再びオンにしたときは保持したチェック状態で戻し、個別に選択されている行を一覧に表示する。この保持方針は合意済み。

分類の一括選択・解除は、非表示中の任務差分・部位も含めた分類全体の選択状態を変更する。この範囲は合意済み。分類のチェックボックスの全選択・未選択・中間状態も、非表示中の項目を含めて判定する。`MISSION VARIANTS`・`TARGET PARTS` 自体のオン・オフは変更しない。例えば部位を非表示にしたまま `AIRCRAFT` を全解除すると、その分類の部位も未選択になり、後から部位表示をオンにしても一覧には現れない。`EXCLUDED` は引き続き選択対象に含めない。

結果表と `TARGETS` の選択欄は、目標の並び順を共通にする。分類順は `AIRCRAFT → GROUND → SHIP → STRUCTURE → OTHER` とし、分類内は目標名順を基本とする。同じ分類内では、同じ目標の任務差分・部位を本体または共通設定の行の直後にまとめ、関連する行を近くで比較できるようにする。本体と異なる分類を個別指定した部位は、その分類内へ配置し、本体の直後に置くために分類をまたがせない。

整理済みの目標リストを流用し、各行を次の6分類のいずれか1つに排他的に分類する。分類名と排他的に扱う方針は合意済み。個々の目標への割り当てと対象範囲の詳細は別途協議する。

| 分類 | 対象範囲の案 |
| --- | --- |
| `AIRCRAFT` | 固定翼機、ヘリ、UAV、飛行船、大型航空機 |
| `GROUND` | 車両、地上砲台、陸上大型兵器、戦闘・索敵・指揮に関わる設備。反撃する海上トーチカ、RADAR TOWER、COMMAND POSTなどの指揮施設を含める |
| `SHIP` | 艦船、船舶、LCAC |
| `STRUCTURE` | 倉庫・格納庫・貯蔵タンク・煙突・パイプライン・柱などの建物・設備・構造物 |
| `OTHER` | SLCM・BVRAAM・MSL DISPENSER（M30）。打ち上げロケット（LAUNCH VEHICLE）と分離部品（LAUNCH VEHICLE DEBRIS）も当面この分類に含める。ALCMは当面掲載対象外 |
| `EXCLUDED` | 現時点の掲載対象から除外する目標。味方用定義として整理した159行、最低HP付きの11行、所属・掲載可否の確認待ち29行、M25の通常モデルを使うHP500の2行、ALCMを含む。除外理由は調査記録で区別する |

`GROUND` と `STRUCTURE` は、上記の具体例を含む分類方針で合意した。建物か車両か、移動可能か、反撃可能かだけで機械的に区分せず、戦闘・索敵・指揮に関わる設備を `GROUND` で探せる構成にする。RADAR TOWERや指揮施設は、直接攻撃の有無だけで `STRUCTURE` に振り分けない。海上のトーチカも、反撃するものは `GROUND` に含める。

分類はマスタで目標ごとに指定する。名称やゲーム内の計算用区分から一律に導出せず、境界が曖昧な目標だけ個別に確認する。海上トーチカの合意を、同じPILLBOX表記の全定義へ無条件に広げない。具体的な割り当てがまだ合意されていない目標は、対象一覧を整理する際に確認する。

部位行の表示分類は、原則として所属する本体と同じ分類にする。ただし、個別に分類を合意した部位は、その指定を優先する。例えば `MAIN ENGINE《LADON》` は `AIRCRAFT`、艦船に属するCIWS・SAM・艦砲は `SHIP`、`AA GUN《LAND DESTROYER》` は `GROUND` とする。`STRUCTURE` に分類した施設の柱・シャッターも `STRUCTURE` に含める。

MEGAFLOATは固定施設として `STRUCTURE` を基本とし、柱・砲塔基部・シャッター・核融合炉は `STRUCTURE` に分類する。`RAIL GUN TURRET` は個別指定の例外として `GROUND` に分類する。この区分は合意済み。砲塔もMEGAFLOATの部位としての関係・部位名《本体名》の表記・`TARGET PARTS` による表示切り替えを維持し、表示分類だけを分ける。

本体に合わせるのは表示分類であり、部位のHP・耐性・`isAir`・`roleGroup` は各部位の確認済みデータを使用する。表示分類の継承を計算条件の継承として扱わない。部位の個別選択は引き続き独立し、本体のチェック状態を自動で引き継がない。

`FRIEND` を `EXCLUDED` に改名し、6分類を維持する。`EXCLUDED` に分類した行はデータとして保持し、結果表・目標選択・検索候補・一括選択・初期選択から除外する。画面で選択できるのは残りの5分類。例えば掲載対象外の航空機は `EXCLUDED` のみに分類し、`AIRCRAFT` には重複させない。独立した味方フラグは設けない。分類は掲載範囲を表し、味方・未使用・恒久的な撃破不能を意味しない。除外理由と元定義との対応は調査記録・初期生成時の対応付けに残し、そのためだけのアプリ配信項目は追加しない。下記の合意済みの対象以外を推測で除外しない。

M25のHP500の目標のうち、次の元定義8行を `EXCLUDED` に分類し、データとして保持したうえで非表示にする方針は合意済み。対象テーブルは `DT_NPC_Mission025day1.json`。NPC・モデル・Blueprintの参照に `Ally` を含むことを確認した。これは静的な参照関係と表示範囲の合意であり、実ゲームで所属を確認したこととは区別する。

| 表示名 | 任務テーブルの行キー | モデル |
| --- | --- | --- |
| TANK | `m1a2_ms25day1_Alpha`、`m1a2_ms25day1_Bravo`、`m1a2_ms25day1_Charley` | `GR010_m1a2_Ally` |
| APC | `stry_ms25day1_Alpha` | `GR013_stry_Ally` |

同任務の通常モデルを参照する `m1a2_common`・`stry_common` も、ユーザーの承認により `EXCLUDED` とする。前者は基礎HP55に任務差分+445、後者は基礎HP20に任務差分+480を加え、いずれも初期HP500・`MinHealth = 0`。除外は `DT_NPC_Mission025day1` のこの2行に限定し、同じNPC・モデルを使用する他任務の通常TANK・APCへ広げない。表示名・HPの一致から味方や既存の除外行との同一性を確定したものではなく、実際の所属は未確認のまま保持する。この2行は下記の命名による199行の抽出集合には含まれない。

追加の[味方候補と掲載対象外の調査](../../../../docs/analysis/friend-candidates/FRIEND_CANDIDATES.md)では、任務行キー・NPC ID・モデルID・Blueprint名のいずれかに `Ally`／`Friend` を含む任務行を199行確認した。このうちモデルまたはBlueprintにも命名根拠がある157行を、任務テーブルと行キーの組を単位として `EXCLUDED` に分類する方針は合意済み。上記のM25の8行と、同任務のHP615のAPC2行もこの157行に含まれる。データとして保持し、結果表・選択候補・検索候補・一括選択から除外する。同じNPC・モデル・表示名を使う別の任務行まで一括して分類しない。この合意は同調査記録に列挙した157行を対象とし、今後名前に `Ally` を含む全定義を自動採用する規則ではない。

残る42行の静的参照を確認したところ、NPC IDにも `Ally` がある21行と、任務行キーだけに `Ally` がある21行に分かれた。前者にはJACKPOT、FLYING MOLE、GREEN、RAFALE M、M22のF/A-18Eが含まれる。後者には通常行と同じNPCを使うTANKやF/A-18C、M24のFRIGATEと対応する艦載砲3基がある。各参照の確認結果は上記調査記録に残し、追加分類の提案と採用済みの157行を区別する。これらの数は統合前の任務行数であり、実ゲームでの所属確認・最終的な表示行数を意味しない。

ユーザーの条件付き承認に従い、後者21行について同じNPCを参照する別の任務行と `values` 全項目を比較した。完全一致が確認できた `DT_NPC_Mission025day1` の `f18c_ally` と `DT_NPC_Mission028` の `gepa_ally` を `EXCLUDED` へ追加し、命名・パラメータ比較を根拠とする対象は計159行とする。比較先の通常行には分類を広げない。残る40行のうち、下記の最低HP付き11行は別の理由で除外する。

後者21行に正の任務HP差分はなく、20行はモデル・NPCの基礎HPと同値、M10の `f18c_Ally` だけHP57から7へ減る。ただし、全パラメータが通常行と一致するわけではない。M24のFRIGATEはHP75、艦載砲3基は各20で、いずれも `MinHealth` の生値が1。同じNPCを参照する別任務行もなく、全項目一致とは確認できない。HP増量がないことと、最低HPを含む計算条件の一致を区別する。この追加確認は最低HPの一般的な表示・計算仕様を確定するものではない。

横断調査の199行のうち、159行と最低HP付き11行の計170行に加え、残る29行も所属・掲載可否の確認待ちとして暫定 `EXCLUDED` とする。この29行はNPC IDにも `Ally` がある21行と任務行キーだけにある8行で、全行の `MinHealth` は0、初期HPは7～75だった。現在の掲載対象からは199行すべてを除外するが、実際の所属や恒久的な除外を確定するものではない。対象29行の任務テーブル・行キー・HPは上記調査記録に列挙する。このうち任務行キーだけに `Ally` がある8行は、個別の詳細確認後にユーザーが `EXCLUDED` 扱いを承認した。残る21行は確認待ちとしての暫定除外を維持する。8行の掲載判断への承認は、実ゲームでの所属確認を意味しない。未確認であることだけを理由に任意の目標を自動除外する一般規則にはしない。ALCMも別途 `EXCLUDED` に分類するが、この199行には含まれない。これらは元定義の任務行数であり、統合後のアプリ用目標数ではない。目標の `EXCLUDED` と兵装の `UNUSED` は別の分類であり、セルの数値・`-`・`?` の判定にも状態を追加しない。

ALCMは、ユーザー指定により当面 `EXCLUDED` に分類し、結果表・目標選択・検索候補・一括選択対象から除外する。元定義と下記の調査記録は残すが、未使用・味方・撃破不能が確認されたことを意味しない。

ALCMについて、ユーザーから該当目標に心当たりがない旨の指摘を受け、同梱データの対応を確認した。`DT_NPC_Mission013.json` の `lacm_01`・`lacm_02` は、それぞれNPC定義 `OP0060_lacm_01`・`OP0060_lacm_02` を参照し、どちらもモデル `OP0060_lacm` に対応する。モデルの表示名キー `ContainerGround_Name_alcm` は `reports/target_display_names.json` で `ALCM` に解決される。モデルHPは15、両NPC・任務行のHP差分は0である。内部名の `lacm` と表示名の `ALCM` は区別する。確認できたのはMission 13の任務テーブルへの登録であり、イベントによる生成・実際の出現・敵味方・攻撃可否を確認済みとは扱わない。

### 3.10 数値で表せないセル

数値で表せない状態は、目標行全体ではなく、目標・兵装・選択した命中条件の組み合わせごとに扱う。次の表示を合意済みとする。

| 状態 | 表示 | 判定条件 |
| --- | --- | --- |
| 撃破不可 | `-` | 選択した計算条件で与えるダメージが0になることを確認できる |
| 未確認 | `?` | 計算に必要なデータや処理が未確認で、値を確定できない |

直撃＋爆風で一方の成分だけが0の場合は、もう一方の成分も含めて判定する。追加爆風を持たない兵装は3.2の決定どおり、その兵装本来の計算を行う。未確認の値を0と仮定して `-` に変換しない。

参照資料で確認できた被ダメージ倍率0の例は次のとおり。これは同梱資料上の静的な設定であり、実ゲームでの測定結果ではない。

| 目標 | 該当する兵装・命中条件の例 |
| --- | --- |
| Mission 8: HARDENED DEPOT（地下弾薬庫） | UGB・RKT。LACM・LAGM・LASMは爆風のみの場合 |
| Mission 27: MEGAFLOAT: TURRET BASE（砲塔基部） | GPB・UGB・RKT・MPBM。LACM・LAGM・LASMは爆風のみの場合 |
| Mission 27: MEGAFLOAT: SHUTTER（中央シャッター） | GPB・UGB・RKT・MPBM |

根拠は `docs/initial/ref/guides/対地編.md` のミサイル・爆弾・ロケット弾・爆風の被ダメージ倍率表、および `DT_NPC_WeaponDurability.json`、`DT_NPC_ExplosionDurability.json`。

「対象外」を独立した状態として設けることは保留する。2026-11-03に既存の参照資料を調査した範囲では、表示対象の兵装・目標・命中条件の組み合わせについて、`-`・`?` とは別の状態が必要となる具体例を確認できなかった。全組み合わせの計算可能性や実際の命中可能性を証明したものではない。

状態の意味や計算前提の説明はドキュメントに置き、画面のセルには数値または記号だけを表示する。最低HPや無敵など、ダメージ0以外の理由による撃破不能の扱いは未確定。

調査では、次の3点を区別した。

| 論点 | 確認した資料と扱い |
| --- | --- |
| ロック可否 | `LockOnTargetType` と `ELiveTargetType` の対応を確認した。ロック対象区分だけでは、命中を仮定したダメージ計算の可否を判定しない |
| 実際の命中可否 | 衝突・範囲判定と被弾処理の記録を確認した。共通の `ObjectTypes` が設定されていても、個々の目標への命中を保証しない。発射条件・飛翔・衝突応答を含む全経路や実ゲームでの命中は未検証 |
| 命中を仮定した計算可否 | 威力、目標HP、兵装耐性、ロール・パーツ補正、HP更新の根拠を照合する。対空・対地の分類や、基本編の補正表の「—」だけから計算対象外としない |

分類をまたぐ具体例として、次を確認した。両例とも命中条件は直撃、目標の初期HPは55、通常耐性は `NPC_WPDur_000`、任務の最低HP設定は0である。

| 目標・兵装 | 設定上のロック対象区分 | 命中を仮定した標準計算の資料 |
| --- | --- | --- |
| Mission 5: TANK（`m1a2_common`）へのQAAM | `BP_plwp_qaam_a0_C` は `AIR_ONLY` | 基礎威力80。QAAMの `WeaponDurabilityCategory` は3で、目標の `Category03` は100%。地上目標であることによる威力・耐性値の欠落はない |
| Mission 3: A-6E（`a06e_common`）への4AGM | `BP_plwp_4agm_a0_C` は `GROUND_ONLY` | 基礎威力80。4AGMの `WeaponDurabilityCategory` は5で、目標の `Category05` は100%。空中目標であることによる威力・耐性値の欠落はない |

この2例は、ロック対象区分から外れることを計算対象外の根拠にできない例である。実際に命中できることや、特殊処理を含む最終的な確定数を検証した例ではない。両兵装の継承後の `ObjectTypes` は同じ3値だが、その一致だけで命中可能とは判定しない。

`DT_LiveWeapon.json` の49行と `DT_NPC_WeaponDurability.json` の37行を照合したところ、兵装が指定する耐性列が欠けていたのはESM・ECM・IEWSの `Category00` だった。それ以外の掲載兵装が指定する耐性列は、37行すべてに存在した。これは列の存在確認であり、全兵装のダメージ処理が確認済みであるという意味ではない。

ESM・ECM・IEWSのBlueprintは `LiveElectronicSupportMeasures` 系で、継承後の抽出プロパティに `Damage` はない。省略をダメージ0とは読み替えない。これらの支援兵装は3.8の合意に従って比較列と選択候補から除外する。表示対象の攻撃兵装と特定目標の間に生じる「対象外」セルの具体例とは扱わない。

同様に、Bot用定義・子兵装・派生形を含む抽出一覧を、そのまま表示兵装一覧にしない。例えば `BP_plwp_msl_Bot_C` の基礎威力60は通常MSLの基礎威力40と区別する。定義の未使用・装備可否を資料から確認できない場合は、静的解析で未使用を確認したとは扱わない。3.8の `UNUSED` 分類は、ユーザーからの情報・指定に基づく表示範囲の決定であり、独立した「対象外」セルを設ける根拠にはしない。

調査の根拠は、`docs/initial/ref/` 配下の次の資料。

- `tables/blueprint_weapons.json` の継承後プロパティと `indexes/native_enums.json` の `ELiveTargetType`。
- `tables/DT_LiveWeapon.json`、`tables/DT_NPC_WeaponDurability.json`、`tables/DT_NPC_ExplosionDurability.json`。
- `tables/DT_NPC_Model.json`、`reports/target_display_names.json`、`reports/mission_enemy_health.json` の対象行。TANKは `GR010_m1a2`、A-6Eは `OP1013_a06e_MS03`。
- `reports/analysis_ja.txt` の `PART_WEAPON_BINDING`、`DURABILITY`、`DIRECT_AND_AREA`、`BLUEPRINT_DEFAULTS`、兵装定義一覧の注意と未確定範囲。補助的に `indexes/native/npc_damage_after_role.asm.txt`、`explosive_collision.asm.txt`、`explosive_to_target.asm.txt` を参照。

TLSの時間計算など、必要な処理が未確認であることを理由に特定目標を恒久的な計算対象外とはしない。資料の検証範囲はSteam build 25201480の静的解析であり、今回も実ゲームでの測定・追加のゲームファイル抽出は行っていない。

### 3.11 PC・スマートフォンへの対応

PC・スマートフォンの双方で、条件の選択と一覧表の確認を行える構成とする。

PC版は、上部の計算条件を左右に分割する案を採用する。主要な配置は次のとおりとする。

| 配置 | 内容 |
| --- | --- |
| 上部左側 | `ROLE`、その下に `PARTS` |
| 上部右側 | `DAMAGE TYPE` |
| 表の直前 | 同じ形式の `WEAPONS`・`TARGETS` ボタン |
| 下部 | 目標・HP・兵装別の確定数一覧 |

PC・スマートフォンともに一覧の固定表示を統一する。横スクロール中は左側の目標名列のみを固定し、HP列は兵装列とともにスクロールする。縦スクロール中は兵装名などの列見出しを上側に固定する。スクロール中も各数値に対応する目標・兵装を確認できるようにする。

スマートフォン版は目標を縦に並べ、表示する兵装を個別に選んで列を絞る方式とする。初回は通常版の `MSL` だけを選択し、目標名・HP・MSLの3列を表示する。MVPでは設定違いを含む兵装の複数選択を許容し、選択した列が画面幅を超える場合は横スクロールを許容する。目標を1つずつ選び直す方式は採用しない。

将来のスマートフォン版は、兵装をツリー構造から単独選択する方式を目指す。複数列による横スクロールの負担を減らすための方針であり、ツリーによる単独選択はMVPの必須要件には含めない。MVPの兵装選択操作は3.8のとおりPC版と共通とする。PC版の初回は全兵装選択を維持する。

スマートフォン版の主画面では、表の上に `WEAPONS`・`TARGETS` ボタンを並べ、その下に目標・HP・確定数の一覧を置く。自機種別、強化パーツ、命中条件は、メニューから開く `SETTINGS` にまとめる。Rookie版MSLと機銃の各Typeは `WEAPONS` で選択する。目標の選択と任務差分・部位の表示切り替えは `TARGETS` 内に置く。この配置は合意済み。

スマートフォンの設定欄は `SETTINGS` を見出しとし、画面右側から画面幅いっぱいに重ねて開くパネルとする。設定の変更は3.12のとおり即時反映し、パネルを閉じると一覧に戻る。設定欄を開く入口は歯車アイコンのボタンとし、`WEAPONS`・`TARGETS` と同じ行の右端に置く。この入口は合意済み。操作部品の配置と結果の見せ方は、PC版と独立して具体化する。

PC版の左右分割、スマートフォン版の主画面・各パネルへの操作の振り分け、設定欄への入口は合意済み。`DIFFICULTY BONUS`・`GUN TYPE` の専用操作を除いた構成で、幅・折り返し・間隔とパネル内部の具体的な配置を全体の画面確認時に調整する。

### 3.12 条件変更の即時反映

自機種別、強化パーツ、命中条件を変更すると、その場で一覧の計算結果を更新する。Rookie版MSLや機銃の各Typeは、他の兵装と同様に選択した列の追加・削除として即時反映する。

兵装・目標の個別選択や分類ごとの一括選択、任務差分・部位の表示設定を変更すると、その場で表示する行・列を更新する。変更を反映するための計算ボタンや適用ボタンは設けない。

### 3.13 選択パネル内の名前検索

MVPから、PC・スマートフォンの `WEAPONS`・`TARGETS` の両方に名前の検索欄を設ける。名前の一部による部分一致で候補を絞り込み、英字の大文字・小文字は区別しない。

検索は選択候補を探すための操作とし、検索語を変更しても個々のチェック状態と結果表の表示行・列は変更しない。候補のチェックを変更した時点で、3.12に従って結果表に反映する。`UNUSED`・`EXCLUDED` の除外と、任務差分・部位の表示切り替えも引き続き適用する。

検索中も、分類の一括選択・解除は検索に一致しない項目を含めた分類全体に適用する。この範囲は合意済み。分類のチェックボックスの全選択・未選択・中間状態も、検索への一致によらず分類全体から判定する。例えば `QAAM` で検索中に `MSL.AIR` を全解除すると、その分類の兵装すべてを解除する。目標側では、任務差分・部位の表示切り替えで隠れている項目も3.9の合意どおり一括操作に含める。`UNUSED`・`EXCLUDED` は選択対象に含めない。

### 3.14 設定の保存・復元

同じブラウザー内に設定を自動保存し、再読み込みや次回アクセス時に復元する。保存対象は次のとおり。この範囲で保存・復元する方針は合意済み。

| 対象 | 保存する内容 |
| --- | --- |
| 計算条件 | 自機種別、強化パーツの選択、命中条件 |
| 表示する項目 | 設定違いを含む個別の兵装・目標の選択状態。非表示中の任務差分・部位の選択状態も含む |
| 目標の表示設定 | `MISSION VARIANTS`・`TARGET PARTS` のオン・オフ |

検索語とパネルの開閉状態は復元対象に含めない。保存がない場合は各節の合意済みの初期値を使う。各節の「初回」は、この保存がない場合を指す。兵装の初期選択はPCで設定違いを含む全兵装、スマートフォンで通常版の `MSL` のみとするが、保存された選択がある場合はその内容を復元する。全解除した選択も有効な設定として保存・復元する。Rookieフラグや機銃Typeは別の状態として保存せず、各兵装定義のIDの選択だけで表現する。

アプリ用データの更新後に保存済みの選択を復元する場合は、兵装・目標とも次の規則を適用する。この方針は合意済み。

| データの更新内容 | 保存済みの選択の扱い |
| --- | --- |
| 同じIDの項目が残る | 選択・未選択を維持する。表示名・表示順・計算用の数値が変わっても、同じIDなら選択を変えない |
| 新しいIDの項目が追加される | 未選択として追加し、表示行・列を自動で増やさない |
| 項目がデータから削除される | そのIDを保存状態から取り除く |

ここでの追加・削除は、アプリのデータ更新によって項目自体が増減することを指す。任務差分・部位の表示切り替えや検索で隠れた項目は削除扱いにせず、既存の合意どおり選択を保持する。全解除を保存していた場合も、更新後に自動選択しない。

保存がない初回アクセスとリセット時は、最新データに対して端末別の初期選択を適用する。PCの兵装は表示対象を全選択、スマートフォンの兵装は通常版MSLのみ、目標は両端末とも表示対象を全選択とする。任務差分・部位の表示フラグは既定どおりオフとし、区分別リセットの対象範囲は3.15に従う。

委任された永続化方式には `localStorage` を採用する。保存対象は小規模な設定と選択IDであり、1つのJSONに保存形式のバージョンとともに保持する。計算結果・配信用マスタ・検索語・パネル開閉は保存しない。読込時に保存形式と現行マスタを照合し、本節の追加・削除・選択保持の規則を適用する。保存への読み書きは計算処理・選択処理から分離する。保存できない場合も現在の画面操作と計算は継続できる構成とし、具体的な例外処理は実装時に検証する。

### 3.15 設定のリセット

計算条件・兵装選択・目標選択の3区分にそれぞれリセットアイコンを設け、その区分の設定を初期値へ戻す。3区分に分ける方針は合意済み。操作した区分の保存内容も更新し、他区分の設定は保持する。

各区分の対象は次のとおり。アイコンの具体的な配置は提案段階。

| 区分 | 初期値へ戻す対象 | アイコンの配置案 |
| --- | --- | --- |
| 計算条件 | 自機種別、強化パーツ、命中条件 | PCは計算条件欄の右上、スマートフォンは `SETTINGS` の見出し横 |
| 兵装選択 | 設定違いを含む個別兵装の選択。PCは表示対象の全兵装、スマートフォンは通常版の `MSL` のみ | `WEAPONS` パネルの見出し横 |
| 目標選択 | 表示対象の全目標を選択し、`MISSION VARIANTS`・`TARGET PARTS` はオフ | `TARGETS` パネルの見出し横 |

全体リセットのボタン名は `RESET` を仮採用する。計算条件・兵装選択・目標選択の3区分をまとめて合意済みの初期値へ戻し、保存内容にも反映する。ラベルは最終確定ではなく、全体の画面確認で見直せるものとする。

全体リセットの配置候補は、PC・スマートフォンともに表の上の操作列の右側。`WEAPONS`・`TARGETS` から間隔を空け、スマートフォンでは右端の歯車ボタンの手前に置く案。この具体的な配置は提案段階。

## 4. 実装仕様

### 4.1 現時点の技術前提

リポジトリの開発規約に従い、React・TypeScript・Vite・pnpmを使用する。保存・復元の対象は3.14、計算関数の入口と結果型は4.10で合意済み。詳細な型、内部構成、状態の保持・永続化の方式、必要な追加依存関係は、合意済みの振る舞いに沿ってエージェントが選定・具体化する。画面は合意済みの構成と提示済みの見本を基準とする。

アプリは静的サイトとして配信する。計算に必要なHP・兵装威力・補正などのデータをアプリに同梱し、確定数の計算はブラウザー内で完結させる。計算条件を変更すると、同梱データを使ってブラウザー内で再計算する。この構成は合意済み。同梱データは4.4の方針で事前生成し、兵装・目標・共通補正の3つのJSONに分ける。生成処理の詳細は今後決める。

### 4.2 計算設計で確認する内容

| 論点 | 確認内容 |
| --- | --- |
| TLSの時間計算 | 資料上の基礎威力40、継続威力18、間隔約0.4秒から、初回命中・継続命中のイベント順序と時刻を確認する。単純なDPS換算や初撃を時刻0とする式は、まだ採用しない |
| HP更新 | float32の演算順序と、HPを10倍した整数として保持する際の丸めを再現する。必要命中数は4.11の反復計算を基準とし、単純な `ceil(HP / 威力)` で全境界を扱わない |
| 特殊な兵装・目標 | 子弾への補正、任務別のHP・耐性、特殊クラスや最低HPなどの適用範囲を確認する。UAVT（内部名 `4uav`）の評価方法・計算単位はISSUE-005で整理する。難易度による敵HPの変化はISSUE-002で調査する |

TLSの秒数表示は合意済みだが、時間計算式は未確定。参照資料ではTLSの継続ヒット全体を検証済みとはしていないため、設定値をそのまま総威力やDPSへ読み替えない。

### 4.3 今後の進め方と判断の分担

確定数の定義・対象範囲、画面と操作、データと計算の基本設計は、各節の合意済み事項を基準とする。残作業は計算の調査・裏取り、具体的な型や内部構成の選定、画面の細部調整、テストと実装計画の具体化であり、基本設計全体を再協議する工程は設けない。

計算系の調査、固定期待値の確定、委任された技術上の選定はエージェントが主体で進める。調査の着手・個々の確認結果・仕様に沿う実装上の細部ごとにユーザーの合意を求めない。未確認の調査結果は事実として採用せず、根拠と検証範囲を記録する。調査から表示値の意味・対象範囲・操作など合意済みの仕様を変える必要が生じた場合や、UAVTの評価単位など利用上の選択が残る場合に絞って相談する。

PC版の画面見本は提示済みであり、画面全体の再承認を一律の着手条件にしない。PC・スマートフォンとも既存の構成・操作の合意に沿って具体化し、残る差分を必要に応じて確認する。余白・文字サイズなどの調整は実際の表示を見て行う。

未解決の調査事項すべての完了を、他の作業の前提にはしない。数値を返す処理は根拠と期待値を確認してから実装し、確認できない組み合わせには既存の `unknown`・`?` の方針を適用する。工程は、実装前に必要な確認と、実装に伴う調査・具体化を分けて整理する。本節は判断の分担を定めるものであり、現段階のアプリ未着手の扱いは1.5に従う。

### 4.4 アプリ用データの生成

参照資料とアプリ側の定義を組み合わせて、アプリ用データを事前生成して保持し、アプリに同梱する。この生成方式は合意済み。

| 内容 | 管理方法 |
| --- | --- |
| HP・威力・耐性・補正などの数値 | 根拠を確認した参照資料から、変換処理で取り込む |
| 表示対象・分類・表示順など | アプリ側の定義として手動で管理する |

生成結果を直接修正せず、参照資料の更新を取り込むかアプリ側の定義を更新して再生成する。元資料の全行をそのまま表示対象とはせず、合意済みの表示範囲を適用する。生成処理・生成データの実装には、設計と実装計画を確定してから着手する。

初期生成用データとアプリ配信用データは分離する。この方針は合意済み。元定義への対応情報や中間結果などの初期生成用データは `.gitignore` の対象とし、Git管理・アプリ配信の対象外にする。アプリ配信用データと生成処理のコードは、この除外には含めない。

配置は次のとおりとする。この配置とGit管理範囲は合意済み。実装時にルートの `.gitignore` へ `/data/local/` を追加する。

| 配置先 | 内容 | Git管理 |
| --- | --- | --- |
| `data/local/` | 初期生成用の定義、固定ID・元定義との対応、中間結果 | 対象外 |
| `src/data/` | アプリ配信用の3つのJSON | 対象 |
| `scripts/generate-data/` | データ生成・検証処理 | 対象 |

生成処理は開発時に手動実行する。アプリは `src/data/` の配信用JSONを直接読み込み、通常の起動・ビルドでは生成処理を実行せず、`data/local/` やローカル参照資料を要求しない。固定IDの対応は `data/local/` の生成用定義に保持し、4.5のとおり再生成による採番し直しを行わない。

配信用マスタはJSON形式とし、`src/data/` 内の次の3ファイルに分ける。この形式と分割は合意済み。

| ファイル | 内容 |
| --- | --- |
| `weapons.json` | 兵装ID・表示名・分類・表示順・ダメージ成分 |
| `targets.json` | 目標ID・表示名・分類・部位／任務属性・HP・耐性倍率・計算用属性 |
| `modifiers.json` | ROLE倍率表、パーツの適用条件・適用段階などの共通定義 |

兵装・目標は、それぞれ表示情報と計算情報を同じレコードに保持する。型はTypeScript側で定義する。生成時にマスタごとのID重複、必要な値の欠落、参照先の欠落を検査する。未確認として許容する明示的な `null` と、必要な項目の欠落は4.13に従って区別する。生成用の対応情報・出典情報は、これらの配信用JSONに含めない。

生成時に上記の不備を検出した場合は失敗として終了し、不備のある行だけを省いて出力しない。3ファイル分の検証がすべて通ってから配信用JSONを更新し、検証失敗時は既存の配信用JSONを変更しない。許容する明示的な `null` は生成失敗の理由にしない。この方針は合意済み。エラーは原因が分かる簡潔なメッセージとし、元テーブル・行キー・項目名を毎回そろえる固定形式までは要求しない。

### 4.5 表示項目のID・属性・出典

表示する兵装列・目標行には、名称や表示順と独立した固定IDを付ける。選択の保存とアプリ内の参照にはこのIDを使う。この方針は合意済み。MSLの通常版・Rookie版、機銃のTypeA/B/Cは、それぞれ別の固定IDを持つ兵装として選択項目・結果列・計算定義を対応付ける。共通行・任務差分行・部位行も、それぞれ独立したIDを持つ。

IDは兵装・目標それぞれのマスタ内で一意な固定の整数とする。この採番方式は合意済み。初回に採番して生成用定義へ保存し、再生成や並べ替えで採番し直さない。追加項目にだけ未使用の番号を割り当て、削除した項目の番号は再利用しない。UUIDは採用しない。ゲーム内のWeaponIDやテーブル行キーとは別のアプリ用IDとして扱う。

IDは一意に識別するためのキーとし、部位・任務・本体との関係をIDの値から読み取る設計にしない。これらの情報は別の属性として持つ。`ladon_main_engine` のような意味を組み込んだ独自キーを必要とせず、表示名や属性の変更でIDが変わらないようにする。倍率を参照するキーはIDとは役割が異なり、4.7のとおり適用先が読み取れる名前を使う。

1つの表示項目とゲーム内の定義は、必ずしも1対1ではない。3.1の方針に従って同条件の複数部位をまとめた表示行は、生成時の対応付けで1つのIDに複数の元定義が結び付く。この対応情報は初期生成用データに保持し、アプリ配信用データには含めない。統合先のIDは再生成時も維持し、配列の位置やHPなどの数値を使って採番し直さない。

#### 4.5.2 属性と生成用定義の構造案

生成用定義とアプリの実行時データを分け、元定義への参照は生成用定義だけに保持する方針は合意済み。次はその構造案であり、フィールド名・具体型は未確定。HP・耐性などの計算データは省略している。

```typescript
type SourceRef = Readonly<{
  table: string;
  row: string;
}>;

type TargetIdentity = Readonly<{
  id: number;
  attributes: Readonly<{
    category: 'AIRCRAFT' | 'GROUND' | 'SHIP' | 'STRUCTURE' | 'OTHER' | 'EXCLUDED';
    partOf: number | null;
    missionVariant: Readonly<{ missionId: string }> | null;
  }>;
}>;

type TargetBuildDefinition = TargetIdentity & Readonly<{
  sourceRefs: readonly SourceRef[];
}>;
```

`partOf` は部位が属する本体のアプリ内IDを参照し、本体行では `null` とする。`missionVariant` は任務固有行を区別する属性とし、共通行では `null` とする。部位と任務差分は独立した属性なので、任務固有の部位行は両方を持てる。タグは自由な文字列の配列に詰めず、用途ごとに型を持つ属性として扱う案。

`sourceRefs` は生成用定義だけに保持し、アプリ配信用データからは除く。これを含む初期生成用データは4.4のとおり `.gitignore` の対象とする。役割は、固定の表示IDに対して数値の取得元と統合する元定義を指定する、生成・検証用の対応表。同条件の左右部位などをまとめた表示行でも、生成時には各元定義を個別に照合できる。

初期データ作成後も、同じ対応表を使って参照資料の更新を取り込める。例えば統合した部位の一方だけでHPや耐性が変わった場合に、同じ表示行にまとめる条件が崩れたことを検出できる。参照先が削除・改名された場合も対応切れを検出できる。この検証に必要な情報は生成用定義に残し、ブラウザーが表示・計算に使わない出典情報を配信データに含める理由にはしない。部品名も必要に応じて生成時の対応情報に保持する。

ある任務表に出典があることと、任務固有の表示行を作ることは分ける。例えば今回確認したM8・M16の左右主エンジンは、抽出表のHP・耐性が一致する。任務表が異なるだけで `missionVariant` を付けず、共通行との差分と合意済みの表示範囲から決める。

### 4.6 目標のHP・耐性を解決する段階

各目標行に適用するHP・通常耐性・爆風耐性は、任務差分を反映して生成時に解決し、その結果をアプリ配信用データに持たせる。この分担は合意済み。

HPはモデル・NPC・任務の設定から、参照資料で確認した演算順序と丸めに従って確定する。耐性はNPC側と任務側の設定から実際に適用する値を決める。通常耐性と爆風耐性は別々に保持し、1つの倍率に合成しない。必要な値や処理が未確認の場合は未確認として保持し、0で補完しない。

ブラウザーは解決済みの目標データと選択した兵装定義を参照し、自機種別・強化パーツ・命中条件に応じてダメージと確定数を計算する。Rookie版MSLや機銃Typeの違いは兵装定義の選択で扱う。元資料のモデル・NPC・任務の設定をブラウザーで再結合する処理は持たせない。

耐性倍率は、各目標が自身の `damageMultipliers` に直接保持する方式で合意した。共通の耐性profileをIDで参照する構造は採用しない。同じ耐性を持つ複数の目標や、HPだけが異なる任務差分行にも、それぞれ解決済みの倍率を出力する。配信用データ内の値は重複するが、生成結果を手修正しない前提のため、profileの同一性判定・採番・参照管理を省き、各目標の内容を直接確認できる構成を優先する。

兵装成分の `targetMultiplierKey` は、選択した目標自身の `damageMultipliers` 内のキーを参照する。直撃と追加爆風で参照先が異なる場合は、4.7のLACMの例のように別のキーで保持し、合算・乗算して格納しない。生成元の共通データは再利用できるが、配信時には各目標へ展開する。ROLE倍率は4.9で合意した共通表のままとする。倍率キーの共有・命名方針は4.7、未確認の数値の表現は4.13に従う。

### 4.7 兵装ダメージの成分単位の構造

兵装の計算定義は主成分 `primary` と追加成分 `additional` に分け、命中条件からの成分選択は共通処理とする。各成分に基礎威力・パーツ倍率の対応 `partMultipliers`・目標側の倍率への参照 `targetMultiplierKey` を持たせる構造は、MPBM・SASM・LACMのサンプルを比較したうえで合意済み。パーツの適用条件・適用段階との分担は4.8に従う。以下はこの構造の例であり、具体的な参照キー名と全兵装を扱う具体型は引き続き検討する。

従前の `componentsByMode` による兵装ごとの対応表、`durabilityRoute` による処理経路の指定、`modifierRule` による兵装専用処理の参照は採用しない。

| 項目 | 意味 |
| --- | --- |
| `primary` | 主成分。物理的な直撃に限定しない。UGBでは爆弾本来の範囲ダメージ、今回のMPBM・SASM・LACMでは直撃が該当する |
| `additional` | 追加成分。MPBMでは範囲初撃、SASM・LACMでは追加爆風。追加成分のない兵装では省略する |
| `baseDamage` | 成分の基礎威力 |
| `partMultipliers` | この成分に作用するパーツと数値倍率の対応。適用条件・適用段階は共通のパーツ定義に持つ。例の空オブジェクトは、評価対象のパーツによる威力補正がないことを確認済みという意味であり、未確認値の補完に使わない |
| `targetMultiplierKey` | 目標側に生成済みの被ダメージ倍率を参照するキー。兵装表示IDや処理関数名ではない |

共通の選択規則は次のとおり。追加成分の有無はデータの構成で決まり、選択中の目標で追加成分のダメージが0になることを理由に主成分へ切り替えない。

| 兵装の構成 | DIRECT | BLAST | DIRECT+BLAST |
| --- | --- | --- | --- |
| 主成分のみ | 主成分 | 主成分 | 主成分 |
| 主成分＋追加成分 | 主成分 | 追加成分 | 両方 |

MPBMの計算定義例。兵装の表示ID・名称・分類などは省略している。

```json
{
  "primary": {
    "baseDamage": 100,
    "partMultipliers": {
      "specialAirPower": 1.12,
      "specialGroundPower": 1.12
    },
    "targetMultiplierKey": "mpbm"
  },
  "additional": {
    "baseDamage": 50,
    "partMultipliers": {},
    "targetMultiplierKey": "mpbm"
  }
}
```

SASMの計算定義例。同じフィールドで基礎威力と適用するパーツの違いを表現する。

```json
{
  "primary": {
    "baseDamage": 50,
    "partMultipliers": {
      "specialAirPower": 1.2
    },
    "targetMultiplierKey": "sasm"
  },
  "additional": {
    "baseDamage": 30,
    "partMultipliers": {},
    "targetMultiplierKey": "sasm"
  }
}
```

LACMの計算定義例。直撃と追加爆風で、目標側の倍率を参照するキーを分ける。

```json
{
  "primary": {
    "baseDamage": 100,
    "partMultipliers": {
      "specialGroundPower": 1.2
    },
    "targetMultiplierKey": "lacm"
  },
  "additional": {
    "baseDamage": 100,
    "partMultipliers": {},
    "targetMultiplierKey": "lacmBlast"
  }
}
```

`specialAirPower` は `AIR.POW+`（元のPartsID 2021802）、`specialGroundPower` は `GND.POW+`（2022802）に対応させるアプリ内キーの案。表示ラベルは別に持つ。各パーツが選択されている場合に該当する倍率を使う。MPBMの直撃には両パーツ、SASMの直撃には対空側だけ、LACMの直撃には対地側だけが作用する。今回の3兵装では、いずれの追加成分にもこれらのパーツは作用しない。

同一成分に作用する複数パーツが選択されている場合、該当する倍率を乗算する。この合成方法は合意済み。MPBMの直撃で `AIR.POW+` と `GND.POW+` を併用した場合は、名目上 `1.12 × 1.12 = 1.2544` 倍となる。適用されるパーツがない場合の倍率は1。成分ごとに適用するパーツを選ぶため、直撃に対する倍率を追加成分へ流用しない。厳密な演算順序と丸めは、次段落の方針に従う。

この対応は、兵装と目標が対空・対地のどちらかという画面分類から推測するものではない。目標条件によって変わる通常ミサイル用パーツは4.8で扱い、`partMultipliers` の値は数値のまま保つ。`partMultipliers` のキーの列挙順を演算順序とせず、パーツ効果の集約・基礎威力への適用・float32演算の境界はゲームの処理に従って別途定める。

目標側には、参照するキーから被ダメージ倍率を引けるデータを生成する。例の `mpbm` は通常耐性の `Category14`、`sasm` は通常耐性の `Category03` に対応する。百分率の100は倍率1、50は倍率0.5として表す。`x40a_WPDur_000` では、MPBM側が100、SASM側が50と確認できる。この耐性定義を適用する目標では、それぞれ `mpbm: 1`、`sasm: 0.5` となる。キー名は参照先を説明するための案であり、武器表示IDからの自動生成や、同じ耐性を参照する他兵装との共有単位を確定したものではない。

MPBMの範囲初撃は爆風フラグ0。SASMの追加爆風は通常の追加爆風の経路だが、専用の爆風耐性への置き換えはLACM・LAGM・LASMに対応するため、SASMも通常耐性の同じ列を参照する。この違いは生成時の対応付けで扱い、ブラウザーの配信用データにゲーム内部の経路フラグを持ち込まない。LACMなどで直撃と追加爆風の適用倍率が異なる場合は、成分に別の参照キーを持たせる。4.6の通常耐性・爆風耐性の分離は維持し、両者を掛け合わせた倍率にはしない。

`targetMultiplierKey` は従前の `durabilityRoute` が担おうとしていた耐性選択を、生成済み倍率への参照に置き換えるもの。パーツ補正の倍率は兵装の成分側に持たせるが、耐性による倍率の実値は目標側に持たせ、兵装の成分にはその参照キーだけを置く。

同じ耐性の参照先を使う成分で倍率キーを共有する方針とする。特定目標で倍率の数値が一致するだけでは共有の根拠にしない。命名では適用先を読み取れることを優先し、`normal03` のように番号だけで区別する名前は避ける。共通化のために曖昧な区分名を作らず、必要なら `lacm` など兵装名を直接使う。複数兵装で共有するキーは、その名前が適用先を誤解させないか対応一覧と照合する。ゲーム内のカテゴリ番号との対応は生成側で保持し、配信用キー名から番号を解析する仕組みにはしない。具体的なキー名と各成分への割り当ては未確定であり、上記サンプルの名前を確定名とは扱わない。

LACMの `lacm` は通常耐性の `Category05` に対応し、`lacmBlast` は追加爆風に実際に適用する倍率に対応する。専用爆風耐性が有効なら `PlayerLACM` で通常耐性を置き換える。専用爆風耐性が適用されず通常耐性を使うことを確認できる目標では、その倍率を生成時に `lacmBlast` 側にも設定する。未確認を通常耐性や0で補完しない。ブラウザーは解決済みの参照先を使うため、この分岐を実行時に再現しない。

具体例として、`DT_NPC` の `VE003_kuzn_01`・`VE005_krov_01` は `LargeShip_WPDur_000` と `LargeShip_ExpDur_000` を参照している。前者の `Category05` は100、後者の `PlayerLACM` は20。これらの設定を適用する目標側の計算データは、該当部分だけを示すと次の例になる。任務差分がある場合は4.6の生成時の解決結果を使う。

```json
{
  "damageMultipliers": {
    "lacm": 1,
    "lacmBlast": 0.2
  }
}
```

この目標に対するLACMは、自機種別補正が1の場合、パーツなしでは直撃100・爆風20、`GND.POW+` ありでは直撃120・爆風20という名目値になる。厳密な演算とHP更新時の丸めは別途扱い、直撃＋爆風でも成分ごとのHP更新を維持する。参照キーが別であることを理由に通常耐性と爆風耐性を二重乗算しない。

パーツだけを適用した名目上の威力は次のとおり。自機種別・目標の耐性・HP更新時の丸めを適用する前の比較であり、厳密なfloat32計算の期待値や確定数ではない。

| 選択パーツ | MPBM 主成分 / 追加成分 | SASM 主成分 / 追加成分 |
| --- | --- | --- |
| なし | 100 / 50 | 50 / 30 |
| AIR.POW+ | 112 / 50 | 60 / 30 |
| GND.POW+ | 112 / 50 | 50 / 30 |
| 両方 | 125.44 / 50 | 60 / 30 |

自機種別補正は、選択した成分それぞれに共通処理で適用する。成分ごとに補正・耐性・HP更新時の丸めを扱い、先に合算して一律の補正や1回のHP更新にまとめない。MPBMの継続ダメージは合意どおり例に含めず、ISSUE-001で保持する。TLSの時間計算をこのサンプルの1命中分の構造に確定するものではない。

数値と計算経路の根拠は `docs/initial/ref/reports/analysis_ja.txt` の `PART_WEAPON_BINDING`・`MPBM_AREA_DEFINITION`・`MPBM_AREA_PARTS`・`MISSILE_AREA_PART_LABELS`・`DURABILITY`、`docs/initial/ref/tables/DT_LiveWeapon.json`、`DT_NPC_WeaponDurability.json`、`DT_NPC_ExplosionDurability.json`。パーツの表示略号は[表示名の調査記録](../../../../docs/analysis/ui-labels/UI_LABELS.md)による。同梱資料の静的解析結果であり、実ゲームでの測定結果ではない。出典は文書と生成用定義に保持し、配信用データに `sourceRefs` は含めない。

### 4.8 パーツ倍率と適用条件の分担

倍率は兵装の成分側、適用条件・適用段階は共通のパーツ定義側に持たせる。この分担は合意済み。`partMultipliers` はパーツのキーから数値倍率を引く対応表とし、数値と条件別オブジェクトを混在させない。

パーツが選択され、その成分の `partMultipliers` に登録され、目標条件を満たす場合にのみ補正を適用する。目標条件に制限がないパーツでも、選択状態と成分への登録は必要。条件に該当するパーツの倍率は、指定された適用段階ごとに乗算する。

通常MSLの成分が持つパーツ倍率の例。キー名は説明用であり、数値は名目値を示す。

```json
{
  "partMultipliers": {
    "missilePower": 1.2,
    "missileAirPower": 1.1,
    "missileGroundPower": 1.1
  }
}
```

共通のパーツ定義で持つ条件と適用段階は、同梱資料に基づく通常MSLの3パーツでは次のとおり。判定方法と適用順序に関する記載の裏取りは[ISSUE-004](ISSUES.md#issue-004-role補正と目標判定に関する同梱資料の裏取り)で行う。データ構造の承認を、ゲーム仕様の検証完了とは扱わない。

| キーの例 | パーツ | 目標条件 | 適用段階 |
| --- | --- | --- | --- |
| `missilePower` | `MSL.POW+`（2014802） | 制限なし | 基礎威力への補正 |
| `missileAirPower` | `MSL.AIR.POW+`（2058802） | `isAir = true` | 自機種別補正の後 |
| `missileGroundPower` | `MSL.GND.POW+`（2059802） | `isAir = false` | 自機種別補正の後 |

`isAir` は目標のゲーム内設定 `bIsAir` に対応する計算用属性。表示分類、目標の名称、座標の高さから推測しない。判定が未確認の目標を `false` として補完しない。

3パーツをすべて選択した場合も、対空・対地パーツのうち目標条件を満たす片方だけが作用する。名目上のパーツ補正は `1.2 × 1.1 = 1.32` 倍となる。ただし通常威力パーツは自機種別補正より前、対空・対地パーツは後に適用されるため、これらを事前に1つの倍率へ合成して一括適用する実装にはしない。厳密な演算順序・丸めはゲームの処理に合わせる。

特殊兵装用の `AIR.POW+`・`GND.POW+` は上記の通常MSL用パーツとは別のパーツであり、これらの名前から対空・対地の目標条件を付与しない。成分側の登録により対象兵装と威力を定め、MPBMでは各1.12、SASMの対空側とLACMの対地側では1.2という差を維持する。

根拠は `docs/initial/ref/reports/analysis_ja.txt` の `PART_COMPOSITION`・`PART_WEAPON_BINDING`・`MSL_TARGET_PART`、`docs/initial/ref/tables/DT_LiveParts.json`。通常MSL用の3パーツはそれぞれパラメーター95・114・115に対応する。適用条件は元データのパーツ名や `SpecialConditionLabel` だけから判断せず、被弾処理での使用経路に基づく。適用条件・適用段階のフィールド名と具体型は未確定。

| 目標の `roleGroup` | 共通のROLE倍率表で参照する目標区分を指定する |

目標側の計算用属性は、例えば次の形となる。キー名と値は構造を説明するための例であり、具体的な目標との対応は元データを確認して生成する。表示分類とは別に保持する。

### 4.10 計算結果と表示の分離

計算の入口は `calculateDefeatRequirement(target, weapon, conditions)` とし、戻り値の型名は `DefeatRequirementResult` とする。この命名と、目標1件・兵装1件・計算条件から撃破に必要な命中数または秒数を求める役割は合意済み。画面・選択状態・保存処理に依存せず、入力から結果を返し、入力を変更しない。表示する行・列の選択と結果の表示整形は画面側が担う。

内部設計は実装時にエージェントが判断する。成分の選択・補正・HP更新・反復処理などを一つの巨大な関数へ詰め込まず、責務に応じて分割する。補助関数の名前や分割数を現段階で固定せず、必要以上の抽象化や階層も設けない。キャッシュを導入するかは4.11の性能対策の方針に従い、今回の命名・役割の合意には含めない。

計算処理は表示用の文字列ではなく、数値または意味を持つ状態を返す。画面側で数値・`-`・`?` へ変換する方針は合意済み。計算結果の形は次のとおり。

```typescript
type DefeatRequirementResult =
  | { kind: "value"; value: number }
  | { kind: "zeroDamage" }
  | { kind: "unknown" };
```

| 結果 | 意味と表示 |
| --- | --- |
| `value` | 撃破に必要な命中数またはTLSの命中秒数を数値として保持し、画面側で表示する。SFFS・SODでは子弾の命中数を表す |
| `zeroDamage` | 選択した計算条件でダメージが0と確認できる組み合わせ。画面では `-` とする |
| `unknown` | 計算に必要なデータや処理が未確認の組み合わせ。画面では `?` とする |

結果の数値は回数・秒数で別の形にせず、共通の `value` として扱う。各セルに単位を重複して持たせず、兵装側にも独立した単位フィールドを必須とはしない。画面の単位表記は合意済みの `TLS [s]` などの列名称で扱う。数値の表示桁数は画面側で扱い、ゲームの計算途中やHP更新時の丸めとは区別する。

「1回あたり、または1秒あたりのダメージ」として計算データを共通化する案は検討候補とする。結果の数値を共通に扱う合意を、TLSを一定の秒間ダメージに換算できることの確認とは扱わない。TLSの初回・継続ヒットの時刻と処理は4.2のとおり未確定であり、時間計算の具体式は調査後に決める。命中数の計算も、既定の成分別の補正・HP更新・丸めを維持する。

`zeroDamage` と `unknown` の判定範囲は3.10に従う。未確認の値を0として扱わず、この結果型に独立した「対象外」状態は追加しない。

### 4.11 必要命中数の基準計算

必要命中数は、1命中分ずつHPを更新する反復計算を基準方式とする。この方式と、高速化は性能上の問題を検知した時点で検討する方針は合意済み。

1. 生成済みの目標の最大HPを開始値とする。
2. 選択した命中条件に対応する成分を順に適用し、成分ごとに補正・HP更新・丸めを扱う。
3. HPが0になるまで1命中分の処理を繰り返し、必要だった命中回数を返す。

直撃＋爆風は両成分を合わせて1命中分と数えるが、HP更新は各成分で行う。SFFS・SODでは子弾1発が1命中分に相当する。各目標・兵装・計算条件の組み合わせは、独立した最大HPから計算する。

基準方式では `ceil(HP / 威力)` に置き換えず、既定の成分別処理とHP更新時の丸めを維持する。0.01倍などの小さい補正倍率が掛かるケースも含め、単純な除算との差が生じる境界を検証する。演算順序・float32の扱い・HPの整数化は、4.2のとおり元の処理と照合して具体化する。

確認済みのダメージ0や計算に必要なデータ・処理の未確認は、3.10・4.10で定めた状態として扱う。本節は必要命中数を返す兵装の計算方式を定めるものであり、TLSの時間計算やUAVTの評価単位は、それぞれの調査・協議結果に従って確定する。

高速化は、実際に表示・操作などの性能上の問題を検知した時点で検討する。性能対策を先取りした仕組みは現段階で追加しない。対策する場合も、この基準方式との結果の一致を確認し、命中数の境界や成分別の丸めを変えない。

### 4.12 設定違いを別の兵装定義として扱う

MSLの通常版・Rookie版と機銃の各Typeは、設定ごとに別の兵装定義を持つ。各定義を `WEAPONS` の選択項目と結果表の列に対応付け、同時に選択して比較できる。この構成と、`DIFFICULTY BONUS`・`GUN TYPE` の専用操作を廃止する方針は合意済み。

| 説明用の呼称 | 基礎威力 |
| --- | ---: |
| MSL 通常版 | 40 |
| MSL Rookie版 | 56 |
| GUN TypeA | 5 |
| GUN TypeB | 15 |
| GUN TypeC | 10 |

各定義の成分は数値の `baseDamage` を持ち、選択した定義を共通の補正・HP更新処理へ渡す。Rookieの真偽値や機銃Typeの選択値を、兵装選択とは別の状態や計算条件として保持しない。通常版とRookie版、複数の機銃Typeを選択した場合は、各列を同じ目標の最大HPから独立して計算する。

選択項目・結果列・計算定義に、定義ごとの固定IDを用いる。表示名が共通の `GUN` でも各TypeのIDは別とし、選択・保存・参照を表示名だけで区別しない。IDは4.5のとおりマスタごとの固定整数とする。種類を示すラベルや同系統のまとめ方は表示側の情報で扱い、IDの値から種類を解析しない。

設定別の定義を持つと共通項目の重複は増えるが、選択した定義の数値をそのまま計算に使え、実行時にRookie・機銃Typeの状態から値を差し替える必要がなくなる。生成時には共通の元データを再利用でき、配信用データは4.4のとおり再生成で更新する。共通部分の具体的な保持方法は、生成データの形式を決める段階で詰める。

基礎データが異なる上記の設定を別定義にし、自機種別・強化パーツ・命中条件は引き続き共通の計算条件として扱う。設定違いの列ラベル・選択肢の記法と並び順の細部は未確定。初期選択と一括操作は3.8、保存・復元とリセットは3.14・3.15に従う。

### 4.13 未確認の数値の表現

計算に必要な数値が未確認の場合は、配信用データに明示的な `null` を格納する。この方式は合意済み。確認済みの0は数値の `0` として保持し、必要なキーの欠落は未確認の表現ではなく生成データの不備として検出する。未確認理由や出典は生成用データ・ドキュメントに残す。

未確認値は少数の例外を想定する。全数値が未確認になり得る前提で一律に型を広げず、具体的に未確認を保持する必要のある項目に適用する。未確認の処理があることと、その処理に使う数値自体が未確認であることは区別する。TLSの時間計算が未確定であることを理由に、確認済みの威力まで `null` に置き換えない。

判定は選択した計算条件で必要な値に限る。説明用の例として `lacm: 1`、`lacmBlast: null` の場合、直撃は他の必要条件が確認済みなら計算でき、爆風・直撃＋爆風は `unknown` を返して `?` と表示する。この例は実データでLACMの倍率が未確認であることを示すものではない。追加成分を持たない兵装など、構造上の省略が認められた項目とは区別する。

## 5. テスト方針

実装時は、開発規約に従って失敗するテストを1つ作成し、`pnpm test` で失敗を確認してから、そのテストを通す最小限の実装を行う。

計算テストには、参照資料と元の処理から確認した具体例を、固定の入力・期待値として保存する。この方針は合意済み。期待値はアプリの計算関数自身で生成せず、根拠と演算順序・丸めを確認して定める。計算関数の変更に合わせて期待値を自動更新しない。静的設定・処理から確認した期待値と、実ゲームで測定した値は区別する。

| 固定の検証例 | 確認する内容 |
| --- | --- |
| 通常MSL | 基本的な命中数と、パーツ・ROLEによる変化 |
| LACM | 直撃と爆風で耐性が異なる目標について、成分別に適用した結果 |
| MPBM | 複数パーツの乗算と、継続ダメージを除いた計算 |
| 0.01倍補正 | 単純除算では再現できないHP更新・丸めの境界 |

TLS・UAVTの具体的な数値テストは、未確定の計算方法を調査してから追加する。未確認状態を `unknown` として返し、画面で `?` にする既存仕様のテストとは区別する。現段階では検証例の種類を合意したものであり、個々の入力値・期待値の確定やテストの実装は行っていない。
