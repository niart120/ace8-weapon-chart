# SWARM DRONESの個体判定と破壊処理

## 表示行の統合（2026-11-04）

HP を非適用にした後、ID 156 と 465 は表示名・計算属性がすべて一致した。ユーザーの重複指摘を受け、掲載行を ID 156 に統合し、出現任務を `[9,10,19,30]` にまとめた。HP `-`・必要命中数 `?` の表示を維持する。元出典は統合先に追加し、ID 465 は元出典と固定 ID を保持して `EXCLUDED` にした。両 ID に HP 非適用の生成規則を適用し続ける。

以下の個体処理の調査と末尾の「両行を掲載」という初回変更は履歴であり、現在の掲載数は 1 行。表示の統合は、M30 と他任務の個体数・挙動が同じと確定した意味ではない。

統合前は公開行が 2 件あるため回帰テストが失敗し、統合後は全 130 テストが成功した。ブラウザーの対象選択・比較表 5 シナリオも成功。1440px/390px で候補と結果が各 1 行、HP `-`・命中数 `?`、HP の昇降順で数値行より後になることを確認した。

## 調査時点

2026-11-04。対象はID156（M9・M10・M19、修正前の配信HP1）とID465（M30、修正前の配信HP20）。調査時点では掲載・計算・生成元を変更せず、後続の承認済み変更を末尾に記載する。

## 結論

群れは個体の位置・識別子を専用配列で管理し、個体単位で命中候補を探す。確認した破壊処理は、正のダメージを条件として個体の除去を予約し、更新時に個体数を減らす。通常NPCのように個体のHPから威力を逐次減算する処理ではない。

HP1とHP20は制御用・システム用NPCのモデル値であり、個体のHPや群れ全体の耐久値と同一視できない。両行を通常の必要命中数計算から外す判断を推奨する。これは計算上の対象外を提案するもので、ゲーム内で破壊できないという判定ではない。

## 個体ごとの命中判定

群れの管理オブジェクトに個体配列があり、個体レコードの間隔は0x90バイト。位置はレコード内の+0x20/+0x28/+0x30、所属側の個体識別子は+0x88として参照される。各小型ドローンが独立した通常NPCであることを示す構造ではなく、専用配列の個体を操作している。

確認した爆発系武器の接触経路は次の順序を取る。

1. `0x147e81850`で武器の`SWDRHitParam.MissileRaidusMeter`（綴りは元定義のまま、+0x8a0）を読む。
2. `0x147e84870`で管理側の`DroneRadiusMeter`（+0x54）を加えた判定半径を作る。メートルから内部距離への倍率は100。
3. `0x147e80060` → `0x147e97ef0` → `0x147e98740`で空間の区画を探索し、個体位置を検査する。最後の関数では通過方向への射影と垂直距離の二乗を計算し、範囲外・半径外の個体を除く。除去待ちの個体も除外する。
4. 命中した個体IDを破壊処理`0x147e84ef0`へ渡す。この呼出しのダメージ引数は固定のfloat32値1で、武器の通常Damageではない（`0x147e81952`、`0x147e819b1`、`0x147e819e8`）。

したがって「群れの大きな一つの当たり判定に当たるだけで全体を破壊する」という処理ではない。判定半径には専用設定を使うため、見た目の小型ドローンのメッシュ形状と正確に一致するという意味でもない。

## 命中から除去まで

`LiveAISwarmDroneManagerGameObject`の被弾用仮想関数（vtable `0x14c572890`、スロット+0xa38）は`0x147e86650`を指し、管理オブジェクトへ転送する。転送先`0x147e849e0`は機銃弾、照射等の`LiveAttachedInstantWeapon`、爆発系武器を区別し、保持している命中個体情報から`0x147e84ef0`を呼ぶ。ここでは入口の型別処理を確認したもので、全兵装の最初の接触からの経路を網羅したものではない。

共通の個体破壊処理`0x147e84ef0`では次を確認した。

- `0x147e84f0d`〜`0x147e84f13`: ダメージが0以下なら終了。
- 連鎖設定と有効な所属グループを調べ、攻撃者情報を更新する。
- `0x147e85136`: 条件を満たした個体IDを`0x147e7f570`へ渡す。

`0x147e7f570`は個体IDをグループ内の範囲で検証し、除去待ち配列+0x120へ重複なしで追加する。HPの減算はしない。グループ更新`0x147e7cd30`がこの配列を消費し、個体レコードの移動・圧縮と個体数の減少を行う。確認した分岐では`0x147e7d1be`で現在個体数+0xfcから除去数を引く。別の分岐でも`0x147e7d0e1`で個体数を減らす。

「正の値なら必ず無条件に破壊」という意味ではない。所属・有効状態などの検査や管理モードの分岐がある。ただし、この処理内でHP1または20に達するまで威力を累積する経路は確認されなかった。

## 連鎖破壊

管理側の`ChainDestructionSetting`（+0x70）から、命中武器のクラスに対応する設定を`0x147e92560`で探す。設定は`TargetWeapon`、`EffectiveRadiusMeter`、`MaxDestructionNum`を持つ。

`0x147e84ef0`は有効半径を読み、個体位置の周囲を`0x147e847b0` → `0x147e7fd40` → `0x147e95050`で検索する。最後の処理では個体との距離の二乗と半径の二乗を比較してコールバックを呼ぶ。

コールバック`0x147e8a480`は元の命中個体を除き、対象個体へ同じ破壊処理を適用する。この再呼出しでは武器ポインターをnullにするため、元武器による同じ設定の再選択を抑えている。処理した個体数を増やし、設定の`MaxDestructionNum`との比較結果を返して探索継続を制御する。比較境界の実際の破壊機数や、同時命中・別の爆風経路との合算は未測定なので、設定値から厳密な総破壊数は提示しない。

これは「威力÷HP」による撃破数ではなく、命中位置・群れの配置・専用半径・連鎖設定に依存する処理である。

## 残る確認範囲

通常版の基底システムは`BP_SWDRManager_ms10_C`、M30版は`BP_SWDRManager_ms30_C`を参照する。任務別のManager・Group・ChainDestructionSettingの実値は今回未読込。群れの初期個体数、補充、武器ごとの半径と最大破壊数は確定していない。ネイティブ既定値だけを任務での実値として採用しない。

全兵装について入口から破壊までを追跡したわけではなく、TLS・UAVなどの命中間隔、特殊武器の爆風、パーツの影響を一律に結論付けない。特に「威力強化は常に無効」「ミサイル1発につき必ず1機」「M30は通常版の20倍硬い」とは判断できない。

両行とも現行アプリの通常HP計算に適合する根拠は不足しており、専用処理が明確に存在する。掲載状態の変更は別途判断する。

## 承認済みの表示・計算への反映

調査後、ユーザーは両行を掲載に残し、必要命中数を`?`、HPを`-`とする方針を承認した。固定ID・名称・分類・任務対応・耐性は維持する。

配信上は`hp: null`（HP非適用）、`standardDamage: false`とする。元モデルのMaxHealth 1／20は抽出資料に保持し、再生成時には`scripts/generate-data/non-hp-targets.json`の指定を適用する。HP非適用と通常計算の矛盾をマスタ検証で拒否する。

表と選択候補のHPは`-`、必要命中数は全兵装・全DAMAGE TYPEで`?`を表示する。HP順では両方向とも数値のある行を先に置く。TYPE・MISSIONの掲載と既存の保存選択を維持する。結果欄の`-`がダメージ0を表す既存の意味は変更しない。

変更前の実データ回帰テストの失敗を確認し、反映後は単体128件、ブラウザー5シナリオ（新規2件は1440／390px）が成功。型検査・Lint・整形確認・ビルドも成功した。配信マスタの差分は両IDの`hp`と`standardDamage`だけである。
